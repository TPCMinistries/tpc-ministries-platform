## 1. ASSESSMENTS

All 6 assessments share one engine: `app/(public)/assessments/[slug]/quiz/page.tsx` (questions hardcoded in TSX) → calculator at `lib/assessments/calculator.ts` → writes to `assessment_responses` + `member_assessment_results` → results page at `app/(public)/assessments/[slug]/results/page.tsx` reads by `?id=`.

**Data source for every assessment**: **Hardcoded in the client component** (not from `assessments`/`assessment_questions` tables). The `/api/assessments/submit-anonymous` and `/submit-member` API routes use `assessments` + `assessment_questions` tables and a *different* calculator — they are **dead code**. Two parallel systems exist.

**Tables touched by the live path**: `assessment_responses`, `member_assessment_results`, `leads`. These tables are **NOT defined in `supabase/schema.sql` or in any migration** under `supabase/migrations/`. The CLAUDE.md-listed tables are `assessments` and `assessment_results` (different names). If the live tables exist in Supabase, they were created out-of-band — schema drift is real and dangerous.

- ⚠ **Results are NEVER emailed.** Email capture saves to `leads`, but no template fires after completion.

## 2. FUNNELS

### a) Signup flow — ✓ WORKING (with caveats)
- Path: `/auth/signup` → `lib/auth.ts:signUp()` → Supabase Auth → DB trigger `handle_new_user` (in `migrations/create_member_on_signup_trigger.sql`) creates `members` row with `tier='free'`. **Tier IS set.**
- After signup, calls `/api/notifications/welcome-email` (fires Resend if `RESEND_API_KEY` set). ✓ WORKING if Resend configured.
- Redirect: signup hardcodes `emailRedirectTo=/api/auth/callback?next=/onboarding`. Confirmation email → `/api/auth/callback` → `/onboarding` → `/api/onboarding/setup-member` → `/welcome` (new) / `/dashboard` / `/kenya-trip` / `/kenya-command-center`.
- ✗ **BROKEN: `?next=` query param is silently dropped.** `app/auth/signup/page.tsx:42` calls `signUp(email, password, fullName)` without forwarding `searchParams.get('next')`; the API callback (`/api/auth/callback/route.ts:25-44`) also overrides `next` when a user/member is found. **Result: handoff `?next=/ask-prophet-lorenzo?handoff=1` never reaches the destination — every signup lands on `/dashboard` or `/welcome`.**

### b) AI public → member handoff — ✗ BROKEN
- Public widget (`components/ai/ask-prophet-widget.tsx`) saves chat history to `localStorage['tpc.ask-prophet.history.v1']` and links to `/auth/signup?next=%2Fask-prophet-lorenzo%3Fhandoff%3D1`.
- Member chat page (`app/(member)/ask-prophet-lorenzo/page.tsx:74-96`) correctly reads the localStorage payload IFF `?handoff=1` is present on the URL.
- **But the auth callback (see above) ignores `next` and redirects to `/dashboard`** — user never lands on `/ask-prophet-lorenzo?handoff=1`. Handoff payload sits in localStorage and is never consumed unless the user manually navigates there before the localStorage entry expires.

### c) Give path — ◐ PARTIAL
- `/giving` → `/api/stripe/create-checkout-session` (one-off + monthly subscriptions) → Stripe Checkout → webhook at `/api/stripe/webhook` records in `donations` and **auto-upgrades giver to `partner` role** (✓ nice touch).
- ✗ **No thank-you/receipt email is fired.** `/api/email/send-donation-receipt/route.ts` exists with a Resend template but **is never invoked by anything** (verified by grep across the repo). No tax receipt.
- ✗ **Membership subscriptions are broken end-to-end.** `/api/stripe/create-checkout/route.ts` (different file) creates `metadata.type='membership'` for Partner/Covenant subscriptions. The webhook handler (`webhook/route.ts:38-46`) has **no branch for `'membership'`** — it falls through to `recordDonation()`, which inserts `type='membership'` into `donations.type` whose CHECK constraint only allows `general|missions|leadership|building|tithe|offering`. The insert will **error**, no tier upgrade, no record. (Also: `/partner` page links to `/partner/upgrade?tier=...` which **does not exist as a route** — confirmed no `app/.../partner/upgrade/page.tsx`.)
- Test vs. live mode: cannot verify without env vars; `STRIPE_WEBHOOK_SECRET` guard in webhook skips signature check if unset (warning logged) — verify it's set in Vercel.
- Donor with no member row → `upgradeGiverToPartner` exits early. No member row created from a guest donation. ◐

### d) Partner application — ✗ BROKEN
- `/partner` (`app/(public)/partner/page.tsx`) is a pricing/FAQ page. The "Become a Partner" / "Join Covenant" buttons link to `Link href="/partner/upgrade?tier=partner"` (line 214) — **this route does not exist**. Clicking returns a 404.
- "Get Started Free" links to `/auth/signup` ✓.
- There is no public partner-application form that writes to the DB. `/api/kenya/partner` is the Kenya-trip partner *dashboard* (auth-gated, irrelevant here).

### e) Kenya 2026 form — ◐ PARTIAL (not the 410 you said)
- `/kenya/page.tsx` declares the trip "complete" in metadata and shows a recap.
- **None** of the Kenya API POST routes return 410 Gone. `app/api/kenya/delegate/route.ts`, `app/api/kenya/travel-form/route.ts`, `app/api/kenya/health-safety-form/route.ts`, `app/api/kenya/kenya-team-signup/route.ts` all accept POSTs and write to DB. Middleware doesn't block them either. If forms exist anywhere (e.g., `/kenya/team`, `/kenya/pack-the-mission`, internal links), they will still process. **Verify your assumption** — the trip API is live, only the marketing copy says "complete."

## 3. NURTURING

### a) Welcome email — ✓ WORKING
- Fires from `lib/auth.ts:signUp` → `/api/notifications/welcome-email` → `EmailTemplates.welcome` (in `lib/email.ts`). Uses `RESEND_FROM_EMAIL || 'noreply@tpcministries.com'`. Verify Resend domain is verified.
- Note: `dashboardUrl` built from `process.env.NEXT_PUBLIC_URL` (not `NEXT_PUBLIC_SITE_URL`) — env var name mismatch likely produces `http://localhost:3000/member/dashboard` in production emails. ⚠

### b) Daily devotional cron — ◐ PARTIAL
- Cron: `/api/cron/daily-devotional` at `0 10 * * *` UTC (vercel.json). ✓ wired.
- Reads `devotionals` + `daily_scriptures` for `today`, falls back to latest published. Sends via Resend to `email_subscriptions` where `subscription_type='daily_devotional' AND is_subscribed=true`.
- Includes optional GPT-4o-mini intro generation per send (cost concern at scale — N OpenAI calls per recipient is fine when small but watch this).
- "From" address is hardcoded `devotional@tpcmin.com` (note: `.com`, not `.org`). ⚠ — must match a verified Resend domain.
- ⚠ No opt-in path is exposed on signup; new members are not auto-subscribed. Subscriber list likely empty.

### c) Email reports cron — ✓ WORKING (internal only)
- `/api/cron/email-reports?type=weekly|monthly` — admin-only, reads `scheduled_report_subscriptions` else falls back to all admins. Not a member-facing nurture.

### d) Streak warnings cron — ✓ WORKING
- `/api/cron/streak-warnings` every 4h. Targets at-risk streaks. Useful retention loop.

### e) Weekly newsletter — ⚠ STUB
- File exists at `/api/cron/weekly-newsletter/route.ts` but is **NOT in `vercel.json` crons**. Never runs. (`weekly-digest` at `/api/notifications/weekly-digest` IS in vercel.json — different route.)

### f) Prayer follow-up — ✗ BROKEN
- `/api/prayer/submit/route.ts` inserts to `prayer_requests` and returns. **No email, no SMS, no admin notification, no in-app notification.** Marked `status='pending'` (admin approval). Users get a UI toast — that's it.

### g) Donor nurture — ✗ BROKEN
- No thank-you email (see Funnels §c).
- No "give again" cadence.
- Recurring donations record successfully but no monthly receipt is emailed.
- `donation-receipt` template is fully written and tested-ready — it just needs to be invoked from the webhook.

### h) SMS — ◐ PARTIAL
- Twilio configured (`lib/sms/twilio.ts`). Only invoked from `/api/admin/sms` and `/api/admin/sms/campaigns/send` — **admin push only**. No automated transactional SMS (no signup, prayer, event, or donation SMS).
- `members.sms_notifications` defaults to `false` at onboarding setup. Even if SMS flows existed, opt-in rate would be 0 by default.

### i) Member lifecycle / upgrade nudges — ✗ MISSING
- No onboarding email series. No "you took an assessment — here's what to do next" sequence.
- No nudge from `free` → `partner` (e.g., after 30d, after 3rd assessment, etc.).
- `email_campaigns` table is logged-to by the devotional cron but no campaign builder runs upgrade flows.

1. **Fix the auth callback to honor `?next=`** (`app/api/auth/callback/route.ts:25-44`). One conditional change unblocks the AI public→member handoff and any other deep-link signup. Also forward `next` from `app/auth/signup/page.tsx` to `signUp()`. **Biggest funnel leak.**
2. **Wire donation thank-you email**: call `/api/email/send-donation-receipt` from inside `recordDonation()` and `recordRecurringDonation()` in `app/api/stripe/webhook/route.ts`. Template is built and ready; takes 10 lines.
3. **Fix or remove the broken `/partner/upgrade?tier=...` link** in `app/(public)/partner/page.tsx:214` and `:318`. Either create the page or point at `/auth/signup?next=...` + handle membership checkout. Right now every Partner/Covenant CTA on the site 404s.
4. **Fix membership Stripe webhook**: add a `metadata.type === 'membership'` branch in `webhook/route.ts` that upgrades `members.tier` + `.role` and DOES NOT insert into `donations` (or relax the donations.type CHECK constraint to include `membership`). Without this, any successful Partner sub silently fails server-side.
5. **Verify `assessment_responses` and `member_assessment_results` tables exist in Supabase + check RLS**. They are absent from migrations. If they don't exist with insertable-by-anon RLS, **every assessment submission is failing right now**. Confirm via Supabase dashboard before launch.
6. **Add prayer-request confirmation + admin notification email** in `app/api/prayer/submit/route.ts`. Currently silent — users have no proof their request was received.
7. **Fix daily-devotional sender domain + subscribe new members by default**. Sender `devotional@tpcmin.com` (.com vs .org) must match the verified Resend domain; auto-insert into `email_subscriptions` on member creation, otherwise the cron has zero subscribers.
8. **Fix the welcome email URL env var**: change `process.env.NEXT_PUBLIC_URL` → `process.env.NEXT_PUBLIC_SITE_URL` in `app/api/notifications/welcome-email/route.ts:15` (and audit any other refs). Every welcome email currently points to localhost in production.
9. **Decide on the assessments dual-system and delete one**. Remove unused `/api/assessments/submit-anonymous` + `/submit-member` + the `assessments`/`assessment_questions` admin path, OR migrate the live quiz page to use them. Maintaining two scoring systems will guarantee bugs.
10. **Confirm Kenya forms are actually intended to be live**. You said they're 410'd — they're not. Either add a 410 response on `kenya/delegate`, `kenya/travel-form`, `kenya/health-safety-form`, `kenya/kenya-team-signup` POSTs, or remove the entry points from public pages. Currently the public can still POST.

**Bonus**: results-page "Download PDF" and "Share" buttons are dead. Either implement or hide before launch — they're visible on every results screen.
